## Design Summary

Инициализировать пустой репозиторий `digital-library` как монорепозиторий из двух независимых сервисов:

- `backend/` — Go-модуль, HTTP API на роутере `chi`, единственный эндпоинт `GET /healthz`.
- `frontend/` — Next.js (App Router, TypeScript, Tailwind) с `shadcn/ui`, pnpm; главная страница дергает `/healthz` на backend и отображает статус — сквозной пример работы связки.

Сервисы не имеют общего build-инструмента (разные экосистемы), но управляются из корневого `Makefile` (`make dev` поднимает оба параллельно). Персистентность, аутентификация, CI и доменная логика самой библиотеки — вне scope, это только каркас. Репозиторий инициализируется как git-репозиторий с одним коммитом скелета.

## Alternatives Considered

Change объединяет несколько независимых структурных решений; альтернативы разобраны по каждому из них.

### Layout монорепозитория

**A: `backend/` + `frontend/` (выбрано)**
- **Approach**: два каталога верхнего уровня, каждый — независимый проект своей экосистемы.
- **Pros**: минимум инструментов, понятно с первого взгляда, ничего лишнего для двух сервисов.
- **Cons**: не масштабируется само по себе на много фронтендов/сервисов.
- **Why not chosen (альтернативы)**: —

**B: `apps/backend` + `apps/frontend` (Turborepo-стиль)**
- **Approach**: apps/ + packages/, готовность к общим JS-пакетам (UI-кит, типы) и нескольким фронтендам.
- **Pros**: масштабируется на много приложений и общий код.
- **Cons**: лишний слой и инструментарий (Turborepo) для двух сервисов без общего JS-кода.
- **Why not chosen**: избыточно на старте — YAGNI, нет второго фронтенда и общих пакетов.

**C: `services/api` + `web/`**
- **Approach**: именование в духе микросервисов.
- **Pros**: подходит, если backend расщепится на несколько сервисов.
- **Cons**: сейчас только один backend-сервис, само название вводит в заблуждение.
- **Why not chosen**: нет предпосылок к нескольким backend-сервисам.

### Роутер для Go-бэкенда

**A: `chi` (выбрано)**
- **Approach**: лёгкий роутер поверх `net/http` с экосистемой middleware.
- **Pros**: идиоматичен, совместим с `net/http` типами, удобные middleware-цепочки и группы маршрутов — пригодится по мере роста API.
- **Cons**: одна дополнительная зависимость.
- **Why not chosen (альтернативы)**: —

**B: stdlib `net/http` (Go 1.22+ ServeMux)**
- **Approach**: без сторонних зависимостей, встроенный мультиплексор с поддержкой методов/параметров пути.
- **Pros**: ноль зависимостей.
- **Cons**: беднее middleware-эргономика по мере роста числа маршрутов.
- **Why not chosen**: для API, которое точно будет расти (это только каркас библиотеки), `chi` даёт задел без реальной цены.

**C: Fiber/Echo**
- **Approach**: полноценный веб-фреймворк с батарейками (валидация, биндинг и т.д.).
- **Pros**: больше готовых возможностей из коробки.
- **Cons**: больше зависимостей и менее идиоматично (Fiber не основан на `net/http`).
- **Why not chosen**: избыточно для одного health-эндпоинта, отходит от идиоматичного Go.

### Момент добавления БД

**A: Отложить БД (выбрано)**
- **Approach**: в этом change — только каркас, `/healthz` без обращения к хранилищу.
- **Pros**: не смешивает scaffolding с доменной логикой, отдельный change для БД получит собственный дизайн (схема, миграции).
- **Cons**: health-check не проверяет реальную зависимость (БД).
- **Why not chosen (альтернативы)**: —

**B: Добавить Postgres сразу**
- **Approach**: Postgres + драйвер + миграции + docker-compose уже в этом change.
- **Pros**: меньше отдельных change для выхода на реальный API.
- **Cons**: увеличивает scope инициализации, смешивает "поднять монорепо" с "спроектировать схему данных".
- **Why not chosen**: пользователь явно попросил отложить — держим change сфокусированным.

### Локальный запуск

**A: Корневой Makefile (выбрано)**
- **Approach**: `make dev/backend/frontend/lint/test`, `make dev` поднимает оба процесса параллельно.
- **Pros**: не требует Docker, работает одинаково у всех разработчиков с `make`, явные и читаемые команды.
- **Cons**: нет изоляции окружения (в отличие от Docker).
- **Why not chosen (альтернативы)**: —

**B: docker-compose**
- **Approach**: оба сервиса в контейнерах с hot-reload.
- **Pros**: ближе к prod-окружению, полезно когда появится БД.
- **Cons**: медленнее dev-петля, лишняя инфраструктура пока нет БД/деплоя для сравнения.
- **Why not chosen**: пользователь выбрал Makefile; docker-compose имеет смысл добавить вместе с БД.

**C: Только инструкции в README**
- **Approach**: без автоматизации, разработчик вручную запускает два терминала.
- **Pros**: нулевые дополнительные файлы.
- **Cons**: неудобно, легко забыть шаг.
- **Why not chosen**: `make dev` даёт удобство почти бесплатно.

## Agreed Approach

Вариант A по каждой оси: `backend/` + `frontend/`, `chi`, БД отложена, корневой `Makefile`. Обоснование выше в каждом разделе — во всех случаях выбор следует YAGNI и соответствует size/scope задачи "поднять каркас монорепозитория", не забегая вперёд в доменную логику или инфраструктуру, которых пока нет.

## Key Decisions

- Два сервиса без общего build-оркестратора; связь только по HTTP/JSON (backend :8080, frontend :3000), CORS на backend для origin фронтенда в dev.
- `backend/`: `cmd/server/main.go` + `internal/`, роутер `chi`, middleware (`slog`-логирование, `Recoverer`, `RequestID`, CORS), `GET /healthz` → `{"status":"ok"}`, конфиг через `os.Getenv("PORT")` с дефолтом `8080` (без viper — одна переменная не оправдывает слой конфигурации), тест на handler через `net/http/httptest`, `.golangci.yml`.
- `frontend/`: `create-next-app` (TypeScript, App Router, Tailwind), pnpm, `shadcn/ui` инициализирован с `button` и `card`, главная страница фетчит `NEXT_PUBLIC_API_URL/healthz` с loading/error state.
- Корневой `Makefile` (`dev`, `backend`, `frontend`, `lint`, `test`) и корневой `README.md` с инструкциями по запуску.
- `git init` в корне, обновлённый `.gitignore` (`node_modules`, `.next`, backend-бинарник, `.env*`), один коммит со скелетом монорепо.
- Вне scope: персистентность/миграции, аутентификация, CI-пайплайн, доменная логика "цифровой библиотеки" (каталог, книги и т.п.) — предмет последующих change.
