## Context

Репозиторий `digital-library` был пуст. Этот change инициализирует его как монорепозиторий из двух независимых сервисов — Go-бэкенда и Next.js-фронтенда — со сквозным примером их связки через health-check. Персистентность, аутентификация, CI-пайплайн и доменная логика самой цифровой библиотеки (каталог, книги и т.п.) сознательно остаются за пределами scope: это только каркас для последующих change.

## Goals / Non-Goals

**Goals:**
- Поднять минимальный работающий монорепозиторий: Go API на `chi` с `GET /healthz`, и Next.js/`shadcn` фронтенд, дергающий этот эндпоинт и отображающий статус.
- Обеспечить единую точку локального запуска обоих сервисов без Docker (`make dev`).
- Зафиксировать git-историю репозитория одним коммитом скелета с корректными игнор-правилами.

**Non-Goals:**
- Персистентность и миграции БД.
- Аутентификация.
- CI-пайплайн.
- Доменная логика цифровой библиотеки (каталог, книги, пользователи и т.п.) — предмет последующих change.
- Docker/docker-compose инфраструктура.

## Decisions

1. **Layout монорепозитория: `backend/` + `frontend/`** (не `apps/`+`packages/` в стиле Turborepo, не `services/api`+`web/`). Два независимых top-level каталога без общего build-оркестратора — минимум инструментов для двух сервисов без общего JS-кода. Turborepo-стиль отложен до появления второго фронтенда или переиспользуемых пакетов (YAGNI); микросервисное именование (`services/`) вводило бы в заблуждение при единственном backend-сервисе.

2. **Роутер для Go-бэкенда: `chi`** (не stdlib `net/http` ServeMux, не Fiber/Echo). `chi` идиоматичен, совместим с типами `net/http`, даёт удобные middleware-цепочки и группы маршрутов, которые понадобятся по мере роста API — цена одной дополнительной зависимости оправдана. Fiber/Echo избыточны для одного health-эндпоинта и менее идиоматичны (Fiber не основан на `net/http`).

3. **Момент добавления БД: отложен.** В этом change `/healthz` не обращается к хранилищу — только подтверждает, что процесс жив. Полноценный БД-слой (схема, миграции, docker-compose) получит собственный change, чтобы не смешивать scaffolding монорепо с проектированием доменных данных.

4. **Локальный запуск: корневой `Makefile`** (не docker-compose, не только инструкции в README). `make dev/backend/frontend/lint/test` не требует Docker, работает одинаково у всех разработчиков и даёт явные читаемые команды. docker-compose имеет смысл добавить вместе с БД, когда появится реальная инфраструктурная зависимость для изоляции.

5. **Конфигурация backend: прямое чтение `os.Getenv`** (без viper или другого слоя конфигурации). Единственная конфигурируемая переменная (`PORT`, плюс `FRONTEND_ORIGIN` для CORS) не оправдывает дополнительную зависимость и абстракцию.

## Risks / Trade-offs

- [Health-check не проверяет реальные зависимости] → `/healthz` подтверждает только то, что процесс жив, а не доступность БД/кэша, которых пока нет. **Mitigation**: следующий change, добавляющий БД, расширит health-check реальной проверкой соединения.
- [Нет изоляции окружения без Docker] → возможны расхождения окружений между разработчиками (версии Go/Node). **Mitigation**: зафиксированные версии в `go.mod` и `pnpm-lock.yaml`; docker-compose добавится вместе с БД, когда изоляция станет более критичной.
- [Два сервиса без общего build-оркестратора] → на монорепозиторий пока нет единого инструмента сборки/кэширования для JS-части. **Mitigation**: если появится второй фронтенд или общий код между фронтендами, тогда стоит мигрировать на Turborepo-подобный layout (`apps/`+`packages/`) — до этого момента усложнение не оправдано.
- [Одна дополнительная зависимость `chi` вместо stdlib] → рост поверхности внешних зависимостей backend. **Mitigation**: `chi` — широко используемая, `net/http`-совместимая библиотека с низким риском; альтернатива (stdlib ServeMux) была явно рассмотрена и отклонена из-за более бедной middleware-эргономики по мере роста API.

## Migration Plan

Не применимо — это greenfield-инициализация пустого репозитория, существующего состояния для миграции нет. Деплой, прод-окружение и стратегия отката вне scope этого change (нет CI/CD, нет доменной логики для развёртывания).
