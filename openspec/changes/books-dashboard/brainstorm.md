## Design Summary

Экран `/books` переделывается из серверно-рендеренного грида карточек с
кнопкой «Показать ещё» в клиентский дашборд-таблицу на базе shadcn data
table (`@tanstack/react-table`). Данные подтягиваются через `fetch` из
браузера (не SSR), таблица использует постраничную пагинацию поверх
существующего `GET /books?limit&offset` (контракт бэкенда не меняется).
В тулбаре таблицы закладывается основа под будущую серверную
фильтрацию (поиск + жанр — живые контролы, но пока ничего не
отправляют на сервер), а действия «Добавить» / «Изменить» / «Удалить»
открывают компонент `Drawer` с формой и вызывают типизированные
заглушки API, которые пока отвечают «не реализовано» через toast.
Postgres поднимается через новый корневой `docker-compose.yml`.
Backend и frontend сразу получают рабочие `.env`/`.env.local` (не
коммитятся, `.env*` уже в `.gitignore`), а соответствующие
`.env.example`/`.env.local.example` актуализируются. Весь новый
пользовательский текст — на русском, в стиле уже существующих строк
(«Моя библиотека», «Показать ещё», «Загрузка…»).

## Alternatives Considered

### Alternative A: TanStack-таблица shadcn + постраничная пагинация + фильтры как «живой, но не действующий» каркас
- **Approach**: `/books` становится клиентским компонентом. Таблица
  строится по каноническому паттерну shadcn `data-table-demo`
  (`columns.tsx` + `data-table.tsx` поверх `@tanstack/react-table`).
  Тулбар: текстовый поиск + селект жанра — состояние в React,
  синхронизировано с URL search params, но не попадает в `fetch`.
  Кнопка «Добавить» и action-меню строки («Изменить» / «Удалить»)
  открывают `Drawer` (shadcn, на `vaul`) с формой
  (`react-hook-form` + `zod`); submit вызывает заглушки
  `createBook`/`updateBook`/`deleteBook`, которые сразу возвращают
  «не реализовано» — UI показывает toast через `sonner`.
- **Pros**: закладывает именно ту «сантехнику» (тип запроса с полями
  фильтров, паттерн Drawer, структура колонок таблицы), которую
  следующий change просто дополнит логикой, не переделывая структуру;
  узнаваемый для будущих разработчиков стандартный паттерн shadcn.
- **Cons**: за один change добавляется заметный набор новых
  зависимостей (`@tanstack/react-table`, `react-hook-form`, `zod`,
  `vaul`, `sonner`); фильтры, которые визуально ничего не делают,
  могут на первый взгляд выглядеть как баг до выхода следующего
  change (смягчается тем, что это внутренний личный проект).

### Alternative B: Оставить самодельный `BooksBrowser`, просто отрендерить `<table>` вручную вместо грида
- **Approach**: Тот же компонент со своим `useState`, но вместо карточек
  — обычная HTML-таблица; над ней — строка с тулбаром, в колонке
  действий — disabled-пункты меню.
- **Pros**: минимум новых зависимостей (не нужны
  `@tanstack/react-table`, `react-hook-form`/`zod`, `vaul`).
- **Cons**: не даёт той основы (сортировка, видимость колонок,
  переиспользуемый паттерн колонок), ради которой явно просили именно
  data table из shadcn; при реальном подключении фильтров/сортировки
  такую таблицу всё равно пришлось бы переписывать под TanStack —
  то есть основа не закладывается, а откладывается на потом.
- **Why not chosen**: прямо противоречит требованию «использовать data
  table из shadcn».

### Alternative C: Вариант A, но фетч через `@tanstack/react-query`
- **Approach**: та же таблица/UI, что в A, но запрос списка книг и
  будущие мутации оборачиваются в `@tanstack/react-query` (кэш,
  инвалидация, retry).
- **Pros**: удобный lifecycle запроса/мутаций — то, что реально
  понадобится, когда CRUD станет настоящим (мутация → инвалидация
  кэша списка).
- **Cons**: ещё одна новая зависимость и `QueryClientProvider` в
  дереве приложения ради одного-единственного запроса и нуля реальных
  мутаций прямо сейчас — преждевременная абстракция под
  гипотетическое будущее.
- **Why not chosen**: заводить `react-query` стоит в change, где
  мутации станут реальными и появится настоящая необходимость в
  инвалидации кэша, а не «про запас» здесь.

## Agreed Approach

Выбран **вариант A**.

- **Backend**: HTTP-контракт `GET /books` не меняется (`limit`/`offset`
  остаются как есть) — фронтенд сам переводит номер страницы в
  `offset = (page - 1) * pageSize`. Единственное изменение backend —
  автозагрузка `.env` в `main.go` (через `godotenv`, тихо
  игнорируется при отсутствии файла — не ломает прод/CI, где
  переменные приходят из окружения напрямую), чтобы `.env` реально
  подхватывался при `go run ./cmd/server`.
- **Docker**: новый корневой `docker-compose.yml` с сервисом
  `postgres:18`, переменными как в README/дефолтах `config.Load`
  (`POSTGRES_USER=postgres`, `POSTGRES_PASSWORD=postgres`,
  `POSTGRES_DB=digital_library`), именованным volume для персистентности
  и healthcheck (`pg_isready`). README переписывается на `docker compose
  up -d` вместо голого `docker run`.
- **Env-файлы**: `backend/.env` и `frontend/.env.local` создаются сразу
  с рабочими локальными значениями (не коммитятся — `.env*` уже в
  `.gitignore`); `backend/.env.example` создаётся впервые,
  `frontend/.env.local.example` актуализируется при необходимости;
  `.gitignore` дополняется исключением для `backend/.env.example` по
  аналогии с уже существующим исключением для
  `frontend/.env.local.example`.
- **Frontend**: `app/books/page.tsx` становится тонкой обёрткой над
  новым клиентским `components/books/books-dashboard.tsx`. Новая
  директория `components/books/`: `columns.tsx` (Title, Author, Year,
  Genre, превью обложки, колонка действий), `data-table.tsx` (обвязка
  над `@tanstack/react-table` + постраничная пагинация), `toolbar.tsx`
  (поиск + жанр, состояние без эффекта на fetch), `book-form-drawer.tsx`
  (добавление/редактирование), `delete-book-drawer.tsx` (подтверждение
  удаления). Старые `books-browser.tsx` и `book-card.tsx` удаляются как
  более не нужные. `lib/api.ts` дополняется типом `BooksQuery`
  (пагинация + необязательные `search`/`genre`, готовые к будущей
  серверной фильтрации, но пока не отправляются) и заглушками
  `createBook`/`updateBook`/`deleteBook`, возвращающими «не
  реализовано». Весь новый UI-текст — на русском.
- **Спека `book-catalog`**: требования «Book List Page» и «Load More
  Pagination» заменяются дельтами на новую страницу-дашборд с
  таблицей и постраничной пагинацией; добавляются требования-заглушки,
  фиксирующие поведение каркаса фильтров и CRUD-заглушек как часть
  контракта (чтобы follow-up change менял именно эти сценарии, а не
  придумывал заново).

## Key Decisions

- Пагинация — постраничная (номер страницы + выбор размера страницы),
  бэкенд-контракт `limit`/`offset` не меняется.
- Фильтры тулбара («поиск» + «жанр») — живые в UI и синхронизированы с
  URL, но не влияют на запрос к серверу до follow-up change.
- Добавление/изменение/удаление — полноценный UI (Drawer + форма с
  валидацией), но submit вызывает заглушку API, которая отвечает «не
  реализовано»; UI сообщает об этом через toast (`sonner`).
- Реальные `.env`/`.env.local` создаются сразу для обоих сервисов
  (не коммитятся), `.env.example`/`.env.local.example` — актуализируются
  и коммитятся.
- Postgres поднимается через `docker-compose.yml` в корне репозитория.
- Весь новый пользовательский текст в интерфейсе — на русском.
- `@tanstack/react-query` в этот change не заводится — преждевременно
  при отсутствии реальных мутаций.

## Open Questions

Нет блокирующих вопросов. Реальная серверная фильтрация и реальные
CRUD-эндпоинты осознанно вынесены в отдельный follow-up change — эта
основа спроектирована так, чтобы тот change был чисто аддитивным
(подключить fetch-параметры фильтров, заменить заглушки на реальные
вызовы), без повторной переделки структуры таблицы/дровера.
