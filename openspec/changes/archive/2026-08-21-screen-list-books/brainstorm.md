## Design Summary

Страница `/books` в домашней библиотеке: карточная сетка с обложками книг, которая читает данные из нового бэкенд-эндпоинта `GET /books`. Библиотека большая (1000+ книг), поэтому список подгружается порциями («Показать ещё»), а не рендерится целиком. В этом изменении — только просмотр: без добавления/редактирования книг, без поиска, сортировки и фильтров (это отдельные будущие изменения).

Данные хранятся в Postgres, таблица `books` (название, автор, год, жанр, обложка — опционально). Раз формы добавления книги пока нет, тестовые данные попадают в БД через seed-миграцию.

## Alternatives Considered

### Alternative A: Тонкий repository-слой поверх `database/sql` + `pgx/v5`, миграции через `golang-migrate`
- **Подход**: `internal/store` — обычный Go-пакет, ручной `rows.Scan` в структуру `Book`, без ORM и без query-builder. Миграции — SQL-файлы в `backend/migrations/`.
- **Плюсы**: полностью соответствует текущему минимализму бэкенда (chi без обёрток, `database/sql` напрямую); `golang-migrate` — стандартный, простой, независимый от рантайма инструмент.
- **Cons**: сканирование строк вручную — чуть больше boilerplate, чем с query-builder.
- **Почему выбрана**: единственная книга-читающая операция (`ListBooks`) не оправдывает дополнительную зависимость; согласуется со стилем существующего кода (`healthz.go`, `router.go`).

### Alternative B: `sqlx` + `goose`
- **Подход**: `sqlx.StructScan` вместо ручного скана, `goose`-миграции на Go, встроенные в бинарник через `go:embed`.
- **Плюсы**: меньше boilerplate на сканировании; миграции не нужно возить отдельно от бинарника.
- **Минусы**: добавляет зависимость (`sqlx`) ради одного запроса; отступает от текущего стиля бэкенда, где нет ни одной обёртки поверх стандартной библиотеки.
- **Почему не выбрана**: не оправдана на этом масштабе (YAGNI), альтернатива A закрывает те же задачи стандартными средствами.

### Alternative C: GORM (ORM)
- **Подход**: полноценный ORM, автомиграции из тегов структуры.
- **Плюсы**: быстрее накидать прототип.
- **Минусы**: тяжёлая зависимость с неявным поведением (хуки, магия запросов), прямо противоречит текущему стилю проекта.
- **Почему не выбрана**: не подходит по духу проекта; отклонена пользователем сразу.

### Alternative D (UI): shadcn `data-table` (TanStack Table) вместо карточной сетки
- **Подход**: построчный список через официальный шаблон `data-table-demo` из реестра shadcn (обёртка над `@tanstack/react-table`: сортировка, фильтрация, пагинация, выбор строк, скрытие колонок).
- **Плюсы**: знакомый табличный паттерн, богатый набор возможностей "из коробки".
- **Минусы**: вся ценность компонента — в сортировке/фильтрации/пагинации, которых в этом изменении сознательно нет; тянет новую зависимость `@tanstack/react-table`; требует `"use client"`, что ломает текущий SSR-подход без спиннеров; обложка книги превращается в мелкую миниатюру в ячейке, а не в узнаваемую карточку — для "домашней библиотеки" визуальное узнавание обложки важнее табличной плотности.
- **Почему не выбрана**: пользователь поднял вопрос в процессе брейншторма — после проверки актуального примера в реестре shadcn выбрана карточная сетка (Alternative A по UI, см. «Agreed Approach»); `data-table` может пригодиться позже, если появится реальная сортировка/фильтрация.

## Agreed Approach

Backend: Alternative A (repository + `pgx/v5` + `golang-migrate`).
Frontend UI: карточная сетка на shadcn `Card` (не `data-table`, см. Alternative D), с постраничной подгрузкой через кнопку «Показать ещё», так как библиотека — 1000+ книг.

## Key Decisions

- **Хранилище**: Postgres, новая таблица `books` (`id, title, author, year?, genre?, cover_url?, created_at`). `title`/`author` — обязательные, остальные поля — nullable.
- **Объём изменения**: только просмотр списка (`GET /books` + страница `/books`). Добавление книг — отдельное будущее изменение (`add-book-form`), пока данные заводятся через seed-миграцию.
- **Пагинация**: `GET /books?limit=50&offset=0`, стабильная сортировка `ORDER BY author, title, id`. Фронтенд рендерит первую страницу через SSR, следующие подгружает клиентский компонент «Показать ещё». Полноценная пагинация по URL/страницам не нужна.
- **Без поиска/сортировки/фильтров и без алфавитных разделителей** — сознательно отложено на будущие изменения, чтобы не усложнять MVP.
- **UI списка**: карточная сетка (не таблица), обложка — `next/image` с фиксированным aspect-ratio и плейсхолдером при отсутствии `cover_url`.
- **Ошибки и пустые состояния**: паттерн как у существующего `fetchHealth()` — discriminated union без throw; пустая библиотека — сообщение без CTA; ошибка бэкенда — текст вместо списка.
