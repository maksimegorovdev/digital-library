# Бэкенд — прагматичный слоистый Clean Architecture: domain → usecase → repository → handler

Бэкенд переходит от текущей плоской структуры (`httpapi` вызывает `store`
напрямую, без промежуточного слоя, `store.Book` — одновременно DB-row и
API-ответ) к явному разделению слоёв: `domain` (сущность + интерфейс
репозитория) → `usecase` (бизнес-логика) → `repository` (было `store`) →
`handler` (было `httpapi`). `domain.Book` становится отдельной сущностью,
не переиспользуемой напрямую как DB-row или API DTO.

Строгая номенклатура Uncle Bob (Entities/Use Cases/Interface Adapters/
Frameworks & Drivers) сознательно не используется — выбран более
идиоматичный для Go вариант именования при сохранении инверсии
зависимостей (интерфейс репозитория определяется в `domain`, реализуется в
`repository`). Usecase-слой вводится сразу, даже при том что текущая
бизнес-логика тривиальна (CRUD книг без сложных правил) — чтобы заложить
явную точку для будущих бизнес-правил и не размывать это решение в рамках
последующих доработок.

Одновременно меняется тестовая инфраструктура: `testify/mock` для моков
репозитория в unit-тестах usecase/handler, `require` вместо `assert`/ручных
проверок stdlib, `testcontainers-go` — для интеграционных и e2e тестов
(поднимают реальный Postgres в Docker; локально Docker уже используется
через `docker-compose.yml`, CI на момент решения отсутствует).

## Considered Options

- Без отдельного usecase-слоя (`domain` → `repository` → `handler` напрямую) —
  меньше boilerplate для чистого CRUD, но отклонено в пользу явного usecase-слоя
  как задела на будущие бизнес-правила.
- Строгая 4-слойная номенклатура Uncle Bob — отклонена как плохо ложащаяся на
  идиоматичный Go; выбрана инверсия зависимостей по существу, без точного
  следования терминологии.
